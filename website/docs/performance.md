# Performance

pipectl is built for small-to-medium batch and ETL work — shaping data in CI, transforming webhook payloads, local dev tooling, config-driven glue between systems. It is **not** a replacement for a distributed engine like Spark: pipectl reads the whole payload into memory, runs it through the pipeline in a single process, and writes the result back out. That design is what makes pipeline behavior simple and predictable (steps like `sort`, `dedupe`, and count-based `assert` can just look at the whole payload), but it also means memory use scales with input size — there's no streaming mode.

The numbers below quantify that envelope: how fast a realistic pipeline runs, and how much memory it actually uses, across file sizes from 10MB up to 1GB — a size chosen deliberately as a practical ceiling for this design, not a technical limit.

## Methodology

- **Pipeline:** a 10-step pipeline — `assert → default → normalize → dedupe → filter → redact → select → rename → sort → count` — run identically across CSV, JSON, and JSON Lines input, so the numbers below isolate format overhead rather than step-selection differences. `cast`/`convert`/`validate-json` are JSON/JSONL-only steps and are intentionally excluded so the three formats are directly comparable. `http-request`/`http-transform` are excluded as I/O-bound — this measures pipeline throughput, not network latency. See [`benchmark/pipeline-csv.yaml`](https://github.com/pipectl/pipectl/blob/main/benchmark/pipeline-csv.yaml) (and the `-json`/`-jsonl` variants) in the repo for the exact definition.
- **Data:** synthetic customer-like records (name, email, country, plan, credit card, signup date, amount, status) generated with realistic value variety — mixed casing, ~5% missing country, ~2% duplicate ids, ~25% inactive status — so every step in the pipeline has real work to do. See [`benchmark/gen`](https://github.com/pipectl/pipectl/tree/main/benchmark/gen).
- **Timing:** `pipectl run --timing`, 5 repetitions per size/format, median reported.
- **Memory:** peak resident set size (RSS) of the `pipectl` process for each run, measured via the OS's own process accounting (`rusage`) — not estimated.
- **Reproduce it yourself:** `go run ./benchmark/run` from the repo root builds pipectl fresh, generates the data, runs the full matrix, and rewrites the results below in place. See [`benchmark/README.md`](https://github.com/pipectl/pipectl/blob/main/benchmark/README.md).

## Reading the memory numbers

"Peak RSS / input size" is the multiplier between a file's size on disk and the most memory pipectl used while processing it. It's consistently well above 1x because the whole file is read into a byte buffer *and* parsed into an in-memory record structure at the same time, and JSON/JSONL carry more per-record overhead than CSV's plain `[][]string`. Use this multiplier to sanity-check `--max-input-size` against the memory available on the machine actually running the pipeline — `pipectl run` also warns if a given `--max-input-size` looks large relative to total system RAM (see the [CLI reference](./cli)).
